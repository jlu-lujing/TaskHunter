# Zmienne środowiskowe

TaskHunter odczytuje te zmienne przy starcie. Dla usług startowych `taskhunter startup enable` domyślnie zapisuje snapshot bieżącego środowiska, więc uruchom tę komendę ponownie po zmianie zmiennych, których ma używać usługa.

## Zmienne dla OpenCode, Git i terminala

Aby przekazać OpenCode, Gitowi, terminalowi i [akcjom projektu](/pl/project-actions/) własne zmienne, na przykład token API albo adres bazy danych, dodaj je w **Ustawienia → Ogólne → Zmienne środowiskowe**, zamiast eksportować je przed uruchomieniem TaskHunter. Wartości zostają na maszynie, na której działa TaskHunter, w pliku `environment.json` w katalogu danych, i może je odczytać tylko Twój użytkownik. Ustawienia nigdy więcej nie pokazują wartości: możesz ją zastąpić albo usunąć, ale nie odczytać.

- OpenCode dostaje je przy starcie, więc po zmianie uruchom go ponownie. Ustawienia mają do tego przycisk.
- Zmienne ustawione przez `opencode service set env` też trafiają do OpenCode. Te z Ustawień mają pierwszeństwo.
- Git, terminal i akcje projektu dostają je przy następnym uruchomieniu.
- Zmienne, które TaskHunter ustawia dla samego OpenCode, jak jego hasło i konfiguracja, mają pierwszeństwo przed Twoimi.

Projekt może dodać własne zmienne albo polecenie, które je wypisuje, na przykład `direnv export json`, w **Ustawienia → Projekty**. Zobacz [Projekty](/pl/projects/#środowisko-projektu).

Te zmienne nie trafiają do serwera OpenCode, który uruchamiasz samodzielnie, a rozszerzenie VS Code nie ma takiego ustawienia. Wszystko poniżej TaskHunter odczytuje sam przy starcie.

## Serwer TaskHunter

### `TASKHUNTER_HOST`

Adres, na którym nasłuchuje serwer web TaskHunter. Użyj `0.0.0.0`, aby pozwolić na dostęp z innych maszyn.

### `TASKHUNTER_LAN_URL`

Adres, pod którym inne urządzenia w sieci łączą się z TaskHunter, na przykład `http://192.168.1.20:3000`. Linki i kody QR do parowania podają go zamiast adresu wykrytego przez TaskHunter. Ustaw go, gdy to wykrywanie się myli, na przykład w Dockerze, gdzie TaskHunter widzi tylko wewnętrzny adres kontenera.

### `TASKHUNTER_UI_PASSWORD`

Hasło do interfejsu w przeglądarce. Ustaw je przy dostępie spoza localhost, tunelach albo reverse proxy.

### `TASKHUNTER_UI_SESSION_TTL_HOURS`

Jak długo trwa logowanie w przeglądarce, w godzinach, gdy opcja „ufaj temu urządzeniu” jest wyłączona. Domyślnie `12`.

### `TASKHUNTER_UI_TRUSTED_SESSION_TTL_DAYS`

Jak długo trwa logowanie, w dniach, na urządzeniu oznaczonym jako zaufane. Domyślnie `7`.

### `TASKHUNTER_API_ONLY`

Uruchamia TaskHunter w trybie headless, gdy ustawione na `true` lub `1`. Trasy API pozostają dostępne dla klientów desktopowych i mobilnych, ale UI przeglądarki nie jest serwowane.

### `TASKHUNTER_FRAME_ANCESTORS`

Originy, które mogą pokazywać TaskHunter w ramce na własnej stronie, rozdzielone spacjami, np. `https://dash.example.com`. `*` dopuszcza dowolną stronę. Domyślnie osadzać go mogą tylko sam TaskHunter i jego aplikacje desktopowe i mobilne, więc żadna inna strona nie nałoży niczego na jego przyciski.

### `TASKHUNTER_DATA_DIR`

Nadpisuje katalog danych TaskHunter. Domyślnie jest to `~/.config/taskhunter`.

Wszystko, co TaskHunter zapisuje, znajduje się w tym katalogu: ustawienia, dane logowania, konfiguracje projektów, motywy, plany i modele mowy. Instancja, która używała własnego katalogu przed wersją 1.23, przy pierwszym uruchomieniu otrzyma kopie folderów `projects`, `themes` i `speech-models` z `~/.config/taskhunter`; oryginały pozostają na miejscu i nic nie jest scalane.

### `TASKHUNTER_CHATS_DIR`

Przenosi katalogi zarządzanych czatów, które TaskHunter tworzy dla czatów bez projektu. Domyślnie jest to `~/.config/taskhunter/chats`. Ustaw katalog, który serwer OpenCode może odczytać, gdy TaskHunter i OpenCode działają jako różni użytkownicy. Istniejące czaty nie są przenoszone.

### `TASKHUNTER_COMPRESS_API`

Steruje kompresją odpowiedzi API. `true` albo `1` ją włącza, `false` albo `0` wyłącza.

### `TASKHUNTER_SKIP_API_COMPRESSION`

Wyłącza kompresję odpowiedzi API, gdy ma wartość `true` albo `1`. Ma pierwszeństwo przed `TASKHUNTER_COMPRESS_API`.

### `TASKHUNTER_VERBOSE_REQUEST_LOGS`

Włącza szczegółowe HTTP request logs, gdy ma wartość `true` albo `1`.

### `TASKHUNTER_UPDATE_API_URL`

Nadpisuje endpoint sprawdzania aktualizacji. Większość użytkowników nie powinna tego ustawiać.

### `TASKHUNTER_PACKAGE_MANAGER`

Wymusza package manager używany do aktualizacji, gdy automatyczne wykrywanie się pomyli.

## Proxy

### `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`

Kieruje przez proxy własne żądania wychodzące TaskHunter, takie jak limity użycia i katalogi skilli. Nazwy pisane małymi literami też działają. Hosty z `NO_PROXY` łączą się bezpośrednio, a `localhost`, `127.0.0.1` i `::1` zawsze, więc wywołania zwrotne logowania i lokalny serwer OpenCode działają dalej.

## Serwer OpenCode

### `OPENCODE_HOST`

Łączy TaskHunter z istniejącym OpenCode server. Wartość musi być origin `http` albo `https` z jawnym portem i bez path, query ani hash. `OPENCODE_HOST` ma pierwszeństwo przed `OPENCODE_PORT`.

### `OPENCODE_PORT`

Ustawia port OpenCode server. Dla managed OpenCode prosi o ten port; z `OPENCODE_SKIP_START=true` łączy się z zewnętrznym serwerem na tym porcie.

### `OPENCODE_SKIP_START`

Gdy ma wartość `true`, blokuje uruchamianie własnego OpenCode server przez TaskHunter.

### `TASKHUNTER_OPENCODE_HOSTNAME`

Hostname dla OpenCode server zarządzanego przez TaskHunter. Domyślnie `127.0.0.1`.

### `OPENCODE_BINARY`

Ścieżka do executable `opencode`, którego ma używać TaskHunter.

### `OPENCODE_CONFIG`

Ścieżka do konkretnego pliku config OpenCode.

### `OPENCODE_CONFIG_DIR`

Ścieżka do katalogu config OpenCode dla agents, skills, snippets i config discovery.

### `OPENCODE_DATA_DIR`

Własny katalog danych dla managed OpenCode server.

### `OPENCODE_WSL_DISTRO`

Wybiera WSL distro używane do integracji OpenCode w Windows.

### `TASKHUNTER_OPENCODE_WSL_DISTRO`

Alias specyficzny dla TaskHunter do wyboru WSL distro. `OPENCODE_WSL_DISTRO` ma pierwszeństwo, gdy ustawione są obie zmienne.

### `OPENCODE_JWT_SECRET`

Secret używany do podpisywania UI auth tokens. Dla trwałych usług użyj długiej losowej wartości.

## Terminal i Git

### `TASKHUNTER_TERMINAL_SHELL`

Shell executable używany przez terminal sessions w TaskHunter.

### `TASKHUNTER_GIT_BINARY`

Git executable używany przez funkcje Git w TaskHunter.

### `GIT_BINARY`

Alternatywny override dla Git executable. Dla konfiguracji specyficznej dla TaskHunter preferuj `TASKHUNTER_GIT_BINARY`.

### `TASKHUNTER_GIT_READ_CACHE_TTL_MS`

TTL w milisekundach dla cached Git-backed file reads. Ustaw `0`, aby wyłączyć cache podczas debugowania.

## Głos i tunele

### `OPENAI_API_KEY`

API key, którego funkcje głosowe TaskHunter używają przy wywołaniach samego OpenAI. Nigdy nie trafia do własnego serwera zgodnego z OpenAI: temu serwerowi podaj osobny klucz w Ustawieniach.

### `TASKHUNTER_ALLOW_REMOTE_OPENAI_COMPAT_URLS`

Pozwala na zdalne OpenAI-compatible base URLs dla funkcji głosowych, gdy ma wartość `true` albo `1`.

### `NGROK_AUTHTOKEN`

ngrok auth token używany przez tunnel commands TaskHunter. Możesz też skonfigurować go przez `ngrok config add-authtoken <token>`.

## Runtime helpers

### `BUN_BINARY`

Bun executable, którego TaskHunter ma używać do uruchamiania daemon processes.

### `BUN_INSTALL`

Katalog główny instalacji Bun. TaskHunter używa go, aby znaleźć `bin/bun` dla daemon startup i aktualizacji.

### `VITE_OPENCODE_URL`

Build-time API base URL dla Vite-built web app. Przy normalnym użyciu CLI lub desktop większość użytkowników nie powinna tego ustawiać.
